# 프로젝트 개발 및 AI 행동 규칙 (Project Development & AI Rules)

## 1. 프로젝트 개요 및 SSOT 원칙
- 본 프로젝트는 교회 주보 제작 자동화 시스템입니다.
- **영역별 SSOT (Single Source of Truth)**: 프로젝트 목적 및 전체 워크플로우는 `README.md`, 환경 및 실행 방법은 `docs/setup-guide.md`, 아키텍처는 `docs/architecture.md`에만 관리합니다.
- 모든 AI의 공통 행동 및 보안 규칙은 `.agents/rules/`, 스킬 원본은 `.agents/skills/`, 워크플로우 원본은 `.agents/workflows/`에만 둡니다.
- 진입점 파일(`AGENTS.md`, `CLAUDE.md`, `.cursorrules`, `.cursor/rules/`)은 위 원본을 참조하는 얇은 래퍼(Thin Wrapper)로 유지하며, 규칙이나 워크플로우 내용을 복제하지 않습니다.

## 2. 크로스 플랫폼 호환성 (Windows & Linux/macOS)
- **실행 환경**: 사용자의 실 운영 환경(Windows PC + 한컴오피스/프린터)과 개발/배포 환경(Linux/WSL/macOS) 모두에서 동작해야 합니다.
- **경로 처리**: 하드코딩된 슬래시/백슬래시 대신 반드시 Python `pathlib.Path` 또는 `os.path.join`을 사용합니다.
- **인코딩**: 모든 텍스트/YAML/JSON 입출력은 UTF-8(`encoding='utf-8'`)을 명시합니다.

## 3. 계획 수립 및 변경 전 설명 (Explain Before Act)
- 복잡한 작업이나 파일 수정 전, 현재 상황과 원인을 파악하고 변경 계획을 먼저 사용자에게 브리핑합니다.
- 임의로 추측하여 과도한 설계를 하지 않으며, 최소한의 외과적 수정(Surgical Changes)을 원칙으로 합니다.

## 4. TDD 및 검증 원칙 (Verification Before Completion)
- 새로운 기능 구현이나 버그 수정 시 `tests/`에 테스트를 먼저 작성하거나 함께 작성합니다.
- 작업 완료 주장 전, 반드시 테스트 및 실행 명령을 직접 수행하여 결과(성공 여부, 에러 코드 0)를 확인한 후 보고합니다.

## 5. 커밋 및 Git 관리 규칙
- **선택적 스테이징**: `git add .`를 금지하고, 수정한 파일만 명시적으로 `git add <file>` 합니다.
- **루트 디렉터리 청결**: 임시 파일이나 생성된 주보 결과물은 루트가 아닌 `output/` 또는 `tmp/`에 저장합니다.
- **메인 브랜치 보호**: `main` 또는 `dev` 브랜치 푸시 전 승인 단계를 거칩니다.
- **커밋 메시지 규칙 (Commit Message Convention)**:
  - **항상 한글 작성 원칙**: 커밋 메시지의 설명 내용은 예외 없이 **항상 한글로만 작성**합니다. 영문 설명은 사용하지 않습니다.
  - **접두어 및 이슈 번호 유지**: 영문 접두어(`<type>:`)와 이슈 번호(`#<이슈번호>`)는 기존 형식을 유지하되, 그 뒤의 모든 설명문은 100% 한글로 기술합니다.
  - **표준 형식**: `<타입>: #<이슈번호> <한글 설명>` 또는 `<타입>: <한글 설명>`
    - 예시: `feat: #12 한글 HWPX 템플릿 치환 엔진 추가`, `fix: 성경 본문 줄바꿈 오류 수정`, `docs: 윈도우 설치 가이드 보완`
  - **준수의무**: 모든 AI 및 작업자는 커밋 작성 시 본 규칙을 필수로 준수해야 합니다.

## 6. 언어 및 소통 정책 (Language & Communication Policy)
- **한국어 기본**: 문서, 주석, 이슈 및 사용자 소통은 한국어를 기본으로 합니다.
- **비개발자를 위한 쉬운 설명 원칙 (Easy Explanation for Non-Developers)**:
  - 본 시스템의 실제 사용자(교역자, 교회 사무원, 평신도 봉사자 등)는 비개발자입니다.
  - 모든 대화 내용, 작업 결과 보고, 오류 안내 및 문서 설명은 난해한 IT/개발 전문 용어(예: 직렬화, XML DOM 파싱, 스택 트레이스, 바이너리 패키징 등)를 지양하고, **비전공자도 즉시 이해할 수 있는 쉬운 일상 용어와 직관적인 설명**으로 풀어 제공해야 합니다.
  - 기술적인 설명이 필요할 경우에도 "사용자 관점에서 실제로 무엇이 달라지는지(예: 한글 표 서식 보존, 클릭 한 번으로 인쇄본 생성 등)"를 중심으로 설명합니다.

  - 사진이 지정된 경우:
    - 원본 사진 파일을 `BinData/image2.png`로 복사하고 `content.hpf` 매니페스트에 등록합니다.
    - 대문 사진 셀(`<cellSz width="52624" height="40060">`) 내부의 문단에 골든 레퍼런스 규격의 `<pic>` 개체(`sz width="51000" height="39780"`, `treatAsChar="1"`, `binaryItemIDRef="image2"`)를 자동 주입합니다.
  - 사진 유무와 무관하게 **사진 칸의 크기(너비 52,624 × 높이 40,060)는 절대 임의 수정하지 않고 원형을 보존**합니다.
- **사진 설명란 (1면 사진 하단)**:
  - 사진이 없을 경우 비워두되, 사진 설명을 구분하는 선인 **`╻` 단 한 줄만 유지**합니다 (두 줄 이상 생성 금지).
  - 4분할 콜라주 등 설명이 2줄로 구성된 경우, 구분선(`╻`) 양식에 맞추어 2개의 독립 문단(`paraPrIDRef="37"`, `charPrIDRef="26"`)으로 단정하게 나누어 기입합니다.
- **셀 치환 시 고유 크기 규격 타겟팅 필수 원칙 (타 표 오염 방지 교훈)**:
  - HWPX 문서에는 여러 표(표지 표, 예배 순서 표, 예배위원 표 등)가 존재하므로, `rowAddr="5"` 같은 단순 행 번호로만 셀을 매칭하여 치환하면 **예배 순서 표의 동일 행(여는찬송·교독송 줄)까지 사진 설명으로 덮어써지는 대참사**가 발생합니다.
  - 따라서 표 내부 셀 치환 시 반드시 고유한 셀 크기 규격(대문 사진 칸: `cellSz width="52624" height="40060"`, 사진 설명란: `cellSz width="52624" height="4581"`)을 복합 매칭하여, 다른 표의 셀이 오염되는 것을 원천 차단해야 합니다.
- **페이지 서식 비율 보존 원칙**:
  - 원고 분량에 따라 유동적으로 조절하는 **예배 순서(2, 3면)를 제외한 다른 모든 페이지(1면 표지, 4면 성경 본문/찬양, 5면 교회소식, 6면 뒷표지)는 표와 칸의 기본 비율을 임의로 수정하지 않습니다**.

## 15. 예배 순서(2, 3면) 소제목 셀 규격 불변 원칙 (Worship Header Cell Sizing)
- **높이 통일**: 징울림, 예배부름, 여는찬송, 교독송, 목회기도, 기도송, 찬양, 성서읽기, 함께읽는말씀 등 모든 순서 소제목 셀은 **표준 소제목 높이(`height="3217"`~`3218`, 약 11.35mm)를 100% 동일하게 유지**합니다.
- **상하 정렬 스타일**: 소제목 셀 내부의 문단은 글자가 한쪽으로 쏠리지 않도록 **상하 여백이 지정된 문단 스타일(`paraPrIDRef="22"`)을 동일하게 적용**합니다.
- **찬양 순서 구조**:
  - 좌측 소제목 셀: 1줄 높이(`3,217`), 불필요한 빈 문단 없는 단일 줄 (`charPrIDRef="37"`, `paraPrIDRef="22"`).
  - 우측 곡명/글·곡 셀: 단일 문단 내에서 반드시 2개의 독립된 런(`<hp:run>`)으로 분리하여 표기합니다:
    - 곡명: 17pt Bold (`charPrIDRef="81"`), 큰따옴표 포함 (예: `“새로운 만남”`).
    - 글·곡 정보: 14pt Regular (`charPrIDRef="93"`), 괄호 포함 (예: ` (글: 이현주, 곡: 백창우)`).
    - 찬양 미정 시 빈칸 유지.
- **HWPX 변조 방지 규격 필수 준수**:
  - 텍스트 치환 시 **`linesegarray` 태그를 100% 완전 제거**하여 한글오피스 보안 경고를 원천 차단합니다.
  - `mimetype` 엔트리는 항상 맨 첫 번째에 비압축(STORED)으로 저장합니다.

## 16. 주보 파일 자동 버전 관리 및 파일 잠금 방지 규칙 (Bulletin Versioning)
- **원칙**: 주보 파일 생성 시 덮어쓰기로 인한 한컴오피스 파일 잠금(`PermissionError`) 및 재실행 번거로움을 방지하기 위해, 항상 버전 접미사(`_v1`, `_v2`, `_v3`...)를 자동으로 부여합니다.
- **명명 규칙**: `output/[주보] YYYYMMDD_v{N}.hwpx` (Typst PDF도 동일 버전 번호 부여).
- **동작 방식**: 기존 파일이 존재하거나 한글 프로그램에서 열려 있는 경우 자동으로 다음 버전 번호로 우회 저장하여, 사용자가 한글 창을 닫지 않고도 새 버전을 열어 즉시 비교·검토할 수 있게 합니다.
- **작업 중간 임시 버전 자동 정리 원칙**:
  - AI가 내부적인 검증, 서식 교정 및 테스트 과정에서 여러 차례 생성하여 버전 번호가 올라간 경우, 사용자에게 완료 보고를 하기 전에 **최종 완성본 1개만 남기고 내부 교정용 중간 버전들은 스스로 자동 삭제·정리**합니다.
  - 사용자는 매 작업 요청마다 폴더 어지러움 없이 최신 완성본 1개만 보고받아 바로 검토할 수 있도록 합니다.

## 17. 예배위원 및 주일 봉사 안내 표기 규칙 (Worship & Service Duty Rules)
- **3개 주일 일자 자동 계산**:
  - 예배위원 표의 3개 주일(당주 w1, 차주 w2, 다다음주 w3) 일자는 기준 주일로부터 7일 간격으로 자동 계산(`MM/DD` 형식)하여 기입합니다.
- **미정 예배위원 빈칸 유지 원칙**:
  - 당회 자료나 원고에 명시되지 않은 미정 예배위원 칸(인도, 목회기도, 성서읽기, 하늘뜻펴기, 감사기도)은 "예배위원", "교우" 등의 임의 단어를 넣지 않고 **반드시 빈칸(`""`)으로 유지**합니다.
- **미정 주일 봉사자 표기 원칙**:
  - 방송실 등 아직 담당자가 확정되지 않은 주일 봉사 항목은 이름을 제외하고 **빈 괄호 `()`만 유지**합니다.
- **HWPX 예배위원 표 그리드 보존 필수**:
  - HWPX 템플릿의 예배위원 3개 데이터 행은 반드시 마스터 템플릿의 12열 그리드 규격(`colAddr: 0, 2, 4, 5, 6, 7`, `colSpan: 2, 2, 1, 1, 1, 2`, 글자 스타일 `charPrIDRef="121"`, 문단 스타일 `paraPrIDRef="74"`)을 유지해야 합니다.
  - 외부 주보 파일에서 다른 열 좌표나 다른 폰트 ID를 가진 셀을 복사해 넣으면 칸 밀림 및 글씨 깨짐이 발생하므로 금지합니다.

## 18. 교독송(국악시편) 표 구조 및 악보 음표 정렬 규칙 (Responsive Hymn & Score Alignment)
- **표 및 연 구조**: 국악시편은 3개 연으로 구성되며, 본문 구절(1a, 1b, 2a)과 후렴 구절(2b)의 행/열을 분리하여 가사가 겹치거나 왜곡되지 않도록 배치합니다.
- **악보 음표 1:1 수직 대응 원칙**:
  - 악보의 음표와 가사 글자는 1:1로 수직 정렬되어야 합니다.
  - 특히 마지막 마디(6개 음표) 아래 가사 배치 시, 이음줄(붙임줄)이 시작되는 **4번째 음표 바로 아래에 마지막 가사 글자**(예: `서`)를 배치하고, **5번째와 6번째 음표 아래에는 각각 이음 부호 `-`를 1개씩 1:1 대응** 배치합니다 (표기 형식: `주  옵소  서  -  -`).

## 19. 하늘뜻펴기(설교) 긴 제목 서식 조절 원칙 (Sermon Title Formatting)
- **우측 빈 칸 병합 너비 확장**: 하늘뜻펴기 행은 우측의 빈 칸을 병합하여 총 너비 39,958 (`colAddr="3"`, `colSpan="6"`)을 확보합니다.
- **폰트 크기 및 장평/자간 표준화**: 하늘뜻펴기 제목은 **17pt(`height="1700"`) 기본 규격을 유지**하며, **장평 90%(`ratio="90"`), 자간 0%(`spacing="0"`), 줄간격 125%(`lineSpacing="125"`)**를 적용하여 우측 칸을 침범하지 않으면서 칸 전체에 당당하고 자연스럽게 1줄로 채웁니다.

## 20. 2면 하단 여백선 일치 및 가사 칸 규격 (Page 2 Bottom Margin & Lyrics Height)
- **함께읽는말씀 본문 칸 밑단 밀착**: 2면 마지막 행(함께읽는말씀 본문)은 2면 하단 여백 경계선에 표 밑바닥이 정확히 닿도록 높이를 확장(`height="7550"` 수준)하여 4~5줄의 긴 말씀도 답답함 없이 여유 있게 배치합니다.
- **성가대 가사 칸 표준화**: 기본 높이에서 한글 단축키 `Ctrl+↑`(약 1mm 축소)를 적용한 표준 높이(`height="4569"`)를 적용하여 상하 여백의 균형을 유지합니다.

## 21. HWPX XML 태그 무결성 원칙 (HWPX XML Tag Self-closing Rule)
- 한글 HWPX 문서 내에서 내용이 없는 속성 태그(예: `hh:ratio`, `hh:spacing` 등)는 반드시 **self-closing 형식(`/>`)을 엄수**합니다 (`<hh:ratio value="86"/>`).
- 닫히지 않은 열린 태그나 불완전한 XML 문법은 한컴오피스 실행 시 "파일 손상" 경고나 강제 종료를 유발하므로 저장 전 XML 구문 검증(well-formed check)을 필수로 거칩니다.

## 22. 공동관심사(소식면) 소주제 체계 및 간격 불변 원칙 (Announcements Structure & Spacing)
- **소주제 기본 6개 체계**: 기본 번호 순서는 `1. 오늘 일정 안내`, `2. 함께 만드는 향린`, `3. 이번주 일정 안내 [M/D(월)-M/D(일)]`, `4. 이후 일정 안내`, `5. 에큐메니칼 소식`, `6. 감사헌금`입니다.
- **교우 소식 유동성**:
  - 교우 소식이 있는 주간에는 `2. 교우 소식`이 삽입되며, 뒤따르는 소주제 번호들이 순차적으로 하나씩 밀려납니다.
  - 교우 소식이 없는 주간에는 해당 항목을 완전 삭제하고 `함께 만드는 향린`이 2번으로 승격됩니다.
- **이후 일정 항시 유지 원칙**:
  - 당장 제공된 차차주 소스가 없더라도 번호 체계와 서식 틀을 보존하기 위해 **`이후 일정 안내` 소주제는 빈 항목으로라도 항상 유지**합니다.
- **소주제 간 간격 6pt 규격**:
  - 소주제와 소주제 사이에 들어가는 빈 문단(`<p>`)은 본문 크기(9.5pt)가 아니라 반드시 **6pt (`height="600"`, `charPrIDRef="125"`)**를 적용하여 여백이 과도하게 벌어지지 않도록 표준화합니다.
- **신도회 모임 공간 박스 자동 삽입**:
  - 둘째 주일 등 신도회 월례회가 있는 주간은 `신도회 월례회` 항목 바로 밑에 신도회별 모임 장소 3줄 안내 표(박스)를 필수 삽입합니다.

## 23. 데이터 절대 임의 추정 금지 및 사전 질문 원칙 (Ask Before Assume)
- **절대 추정 금지 (No Assumptions)**:
  - AI는 그 어떤 데이터(성서 본문, 일정 날짜, 모임 주기, 예배위원 명단, 사유 문구 등)도 **자의적으로 지레짐작하여 확장하거나 기입하지 않습니다**.
- **모임 주기 맹신 및 +7일 기계적 계산 금지 (금향로 기도회 교훈)**:
  - 금향로 기도회처럼 월 1회 열리는 모임은 교회 사정에 따라 주차(원래 셋째 주, 상황에 따라 둘째 주 등)가 유동적이므로, 기계적으로 +7일 더하거나 주차를 임의 계산하지 않고 **오직 공식 확정 자료(당회록, 목운위 자료)에 명시된 일정만 기입**합니다.
- **모호성 발생 시 즉시 질문 원칙**:
  - 원고나 소스가 불확실하거나 모호할 경우, 자의적으로 추정하여 일을 그르치지 말고 **반드시 사용자에게 먼저 질문하여 확인을 받은 후 기입**합니다.
- **성서일과 홈페이지 교차검증 엄수**:
  - `이번주 성서일과`는 추정하거나 임의로 작성하지 않고, 반드시 공식 홈페이지(`목회마당 > 이번주 성서읽기`)에서 **다음 주일 일자 게시글**을 직접 조회하여 `제1성서(구약), 제2성서(서신서), 복음서` 순으로 정확히 대조 기입합니다 (2주 뒤 본문을 잘못 가져오는 오차 원천 차단).

## 24. 불릿 기호 정렬 보호 및 타이포그래피 미학 (Bullet Alignment & Typography)
- **불릿 기호(`∙ `) 자간 0% 보존**:
  - 모든 소식 항목의 글머리 기호(`∙ `)는 **항상 자간 0%(`charPrIDRef="79"`)의 독립된 런으로 분리**하여, 본문 자간을 줄이더라도 전체 들여쓰기 라인이 왼쪽으로 무너지지 않도록 보호합니다.
- **과부(외톨이 글자) 방지 미세 자간 및 줄바꿈 (인간의 융통성)**:
  - 문장 끝에 한두 글자만 다음 줄로 삐져나오는 과부 현상을 방지하기 위해, 불릿 이후 본문 전체의 자간을 -1%~-7% 미세 조절하거나 자연스러운 끊어읽기 위치(예: 향린국악학교 `서도민요반` 뒤)에서 줄바꿈(`<lineBreak/>`)을 적용하여 조판의 완성도를 극대화합니다.

## 25. 공동관심사(소식면) 줄간격 기준 및 유동 조절 원칙 (Announcements Line Spacing Rules)
- **소주제 헤더 130% 불변 고정**:
  - 6개 소주제 헤더 문단(`paraPrIDRef="94"` 및 `"70"`)의 줄간격은 **항상 130%로 불변 고정**합니다.
- **소식 내용 기본 170% 및 분량별 유동 조절**:
  - 소식 항목 본문 문단(`paraPrIDRef="102"`)의 기본 줄간격은 **170%**로 설정합니다.
  - 소주제는 고정이나, 본문 내용은 주간별 원고 분량에 따라 5, 6면 전체 여백 균형에 맞춰 유동적으로 조절(160%~180%)될 수 있습니다.
  - **3페이지 초과 시 5% 단위 축소 원칙**: 광고/소식 항목이 많아져서 3페이지로 넘어갈 경우, 소제목은 그대로 두고 내용 부분의 줄간격을 **5%씩 줄여(170% → 165%) 2페이지(5, 6면) 내에 맞춥니다**.

## 26. 사용자 수동 편집 에셋(QR코드/포스터 사진) 보존 및 인계 원칙 (Manual Asset Preservation Rules)
- **원칙**: 사용자가 한컴오피스 등에서 특정 소식 항목이나 페이지에 수동으로 첨부/삽입한 이미지 개체(예: `길목 청년활동가 지원 사업`의 QR코드 `2gtkk.png` 등)는 AI가 다음 주보를 재빌드하거나 새로 생성할 때 절대 삭제되거나 유실되지 않고 영구 보존되어야 합니다.
- **자산 보관소**: 사용자가 삽입한 이미지 파일은 `data/assets/images/`에 원본 바이너리로 영구 보관합니다.
- **HWPX 패키징 동기화 및 악보 이미지 충돌 방지 필수**:
  - **교독송 악보 보호**: 템플릿의 교독송 후렴 악보(`BinData/image6.bmp`)와 절대 충돌하지 않도록, QR코드 등 외부 추가 에셋은 **독립된 고유 번호(`image8.png`, ID `image8`)**로 주입합니다. 기존 템플릿의 악보 이미지(`image6.bmp`)를 절대 삭제하거나 덮어쓰지 않습니다.
  - `Contents/content.hpf` 매니페스트에 올바른 미디어 타입(`image/png`)으로 `image8`을 자동 갱신/등록합니다.
  - XML 렌더링 시 해당 항목 문단 내에 사용자의 그림 개체(`<hp:pic>` / `<ns1:pic>`) 속성(크기, 여백, z-order, 좌표)을 정확히 인계하여 렌더링합니다.
- **길목 청년활동가 QR코드 표준 규격 확정값**:
  - 사용자가 조정한 최적의 시각적 규격: 선택 크기 `sz width="2321" height="2321"`, 현재 크기 `curSz width="2321" height="2321"`, 조절점 중심 `centerX/Y="1160"`, 변환 행렬 `e3="-24439"`, 배율 `scaMatrix e1/e5="0.086734", e3="24439"`, 가로 위치 `horzOffset="49176"`.
- **YAML 메타데이터 연동**: 입력 YAML에 `image:` 필드로 지정하거나, 해당 소식 항목에 자동 바인딩되도록 관리합니다.

## 27. 등록 새교우 명단 순환 배치 및 서식 보존 규칙 (New Members Placement Rules)
- **배치 위치**: 주보 7면 상단 `▯등록 새교우 (2026)` 표.
- **배치 원칙**: 당회/목운위 자료에 신규 등록 교우가 있을 경우, 해당 교우(예: `김은주(새청, 9/06)`)를 표의 **맨 앞(1행 1열)**에 새로 기입하고, 기존 교우들의 명단은 순차적으로 한 칸씩 뒤로 밀어 기입합니다.

## 28. 교회 전화번호 표기 순서 규칙 (Church Telephone Number Rules)
- **표기 원칙**: 교회 대표전화번호는 **반드시 `776-9141, 3806` 순서 (9141 우선)**로 표기합니다.
- 이전 구 순서(`776-3806, 9141`)는 사용하지 않습니다.
- 8면(뒷표지) 교회 기본 정보 텍스트 및 주보 내 연락처 안내 시 100% 동일하게 준수합니다.

## 29. HWPX 고정 서식 및 박스 내부 레거시 텍스트 전수 치환 불변식 (Hardcoded Box Sanitization)
- **원칙**: 주보 원고(YAML) 데이터 치환뿐 아니라, HWPX 생성 엔진(`hwpx_engine.py`) 내부에서 프로그래밍 방식으로 주입되는 고정 표/박스(예: 5면 신도회 월례회 모임 장소 박스) 및 템플릿 기본 텍스트(8면 교회 정보)에 과거 구 표기나 구 전화번호가 하드코딩되어 있지 않은지 전수 점검·치환합니다.
- **필수 동기화 항목**:
  1. 5면 신도회 모임 장소 박스: `청녀, 희녀, 장녀` (구 표기인 청여, 희여, 장여 잔존 원천 차단)
  2. 8면 교회 기본 정보: `전화: 776-9141, 3806` (템플릿 기본값 자동 보정)

## 30. 사용자 수동 편집 사전 자동 감지 및 무손실 계승 원칙 (Auto-detect & Non-destructive Succession of Manual Edits)
- **원칙**: 사용자가 한컴오피스 등에서 주보 파일(HWPX)을 직접 수정(텍스트 변경/추가, 서식 미세조정, QR코드/이미지 삽입 등)한 후 새로운 작업을 요청할 경우, 사용자가 "기억해줘"라고 명시적으로 말하지 않더라도 **반드시 작업 착수 전 최신 출력본 HWPX의 변경 여부를 스스로 확인하고 무손실로 계승**해야 합니다.
- **작업 착수 전 선행 감지 절차**:
  1. **수정 시각(타임스탬프) 대조**: 새로운 수정이나 빌드 지시를 받으면, 가장 먼저 `output/` 내 최신 HWPX 파일의 최종 수정 시각을 확인합니다. AI가 마지막으로 생성한 시각보다 더 늦게 저장된 기록이 있으면 '사용자 수동 편집 발생'으로 자동 판정합니다.
  2. **선행 역동기화 (Reverse Sync)**: 새 요청 작업을 진행하기에 앞서, 사용자가 수정한 최신 HWPX 파일을 파싱하여 다음 항목들을 즉시 추출하고 시스템 기억(`input/bulletin_YYYYMMDD.yaml` 및 `data/assets/images/`)에 영구 반영합니다:
     - 새로 추가되거나 수정된 소식/행사 문구 및 일정
     - 사용자가 직접 삽입한 그림/QR코드 바이너리 (`BinData/`) 및 문단 내 위치 규격
     - 사용자가 다듬은 성경 본문/찬양/예배위원/기도문 등의 단락 및 줄바꿈 서식
  3. **누적 증분 빌드**: 사용자의 수동 편집본(A)을 온전히 보존한 상태에서 사용자가 새롭게 요청한 작업(B)을 덧붙여 다음 버전(`_v{N+1}.hwpx`)을 생성합니다.
- **금지 사항**:
  - 사용자가 한글 프로그램에서 직접 공들여 수정한 내용이 존재함에도, 이를 검사하지 않고 이전 원고(YAML) 기준으로 덮어써서 사용자의 편집분을 유실(롤백)시키는 행위를 엄격히 금지합니다.
