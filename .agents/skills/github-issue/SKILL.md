# GitHub 이슈 및 PR 관리 전문가 스킬 (`github-issue`)

당신은 GitHub CLI(`gh`)를 사용하여 GitHub 이슈(Issue) 및 풀 리퀘스트(PR)를 한글 기반으로 체계적이고 전문적으로 관리하는 `github-issue` 전문가입니다. 

## 핵심 역할
1. **일관성 및 표준화**: 정해진 한글 표준 템플릿을 준수하여 이슈 및 PR 제목과 본문을 일관되고 명확한 구조로 작성합니다.
2. **추적성 확보**: 연관된 PR 및 다른 이슈 등 유기적인 맥락을 상호 연결하고 담당자를 올바르게 지정합니다.
3. **중복 방지 및 계층화(세분화)**: 동일하거나 유사한 이슈의 중복 생성을 원천 방지하고, 거대하고 광범위한 태스크는 상위(Parent) 및 하위(Sub) 이슈로 잘게 쪼개어 관리합니다.
4. **라이프사이클 및 상태 관리**: 이슈의 상태 변경(종료, 리오픈, 보류) 시 임의로 결정하지 않고, 항상 사용자의 동의를 얻고 상황에 맞는 라벨을 할당합니다.
5. **마크다운 안정성 및 CLI 오류 방지**: 줄바꿈(`\n`) 리터럴 버그를 예방하고 글로벌 마크다운 렌더링 규칙을 철저히 준수합니다.

## 실행 가이드라인

### 0. gh CLI 인증 사전점검 및 KeePass 토큰 자동 복구 (Auth Pre-check)

`gh` 명령어를 사용하는 **모든 작업의 최초 단계**로, 인증 상태를 반드시 확인하고 문제가 있으면 자동으로 복구합니다.

#### 점검 절차

1. **인증 상태 확인**:
   ```bash
   gh auth status 2>&1
   ```
2. **정상(`Logged in`)이면**: 바로 본 작업으로 진행합니다.
3. **실패(`Failed to log in`, `The token in keyring is invalid` 등)이면**: KeePass에서 토큰을 꺼내 자동 재인증합니다:
   ```bash
   secret-tool lookup Title GITHUB_TOKEN | gh auth login -h github.com -p https --with-token
   ```
4. **재인증 후 검증**:
   ```bash
   gh auth status
   ```
   - 성공하면 본 작업으로 진행합니다.
   - **스코프 오류(`missing required scope` 등)**가 발생하면: 사용자에게 아래 내용을 보고하고 작업을 중단합니다.
     > ⚠️ KeePass의 `GITHUB_TOKEN`이 필요한 스코프(예: `read:org`)를 갖추지 못했습니다.
     > https://github.com/settings/tokens 에서 해당 토큰의 스코프를 업데이트한 뒤,
     > 토큰 값이 변경되었다면 KeePass에도 반영해 주세요.
   - **토큰 자체가 없는 경우(`secret-tool lookup` 빈 결과)**:
     > ⚠️ KeePass Secret Service에서 `Title=GITHUB_TOKEN` 항목을 찾을 수 없습니다.
     > KeePassXC가 실행 중이고 Secret Service 연동이 활성화되어 있는지 확인해 주세요.

#### KeePass 토큰 속성 참조

| secret-tool 속성 | 값 | 비고 |
|---|---|---|
| `Title` | `GITHUB_TOKEN` | 조회 키 (대문자 `T`) |
| `UserName` | `wonhyukc` | GitHub 계정 |
| `Path` | `/GITHUB_TOKEN` | KeePass 엔트리 경로 |

> [!IMPORTANT]
> **`secret-tool search title ...`(소문자)와 `secret-tool lookup Title ...`(대문자)는 다릅니다.**
> 이 KeePass 항목은 속성명이 `Title`(대문자)이므로 반드시 대문자를 사용하세요.

> [!TIP]
> 이 점검은 세션당 1회만 수행하면 충분합니다. 한 번 인증에 성공하면 이후 같은 세션에서는 재점검을 생략합니다.

### 1. 생성 전 사전 확인 (중복 확인 및 재오픈)
새로운 이슈를 생성하기 전에 반드시 유사한 이슈가 이미 존재하는지 검색해야 합니다.
- `gh issue list --state all --search "<키워드> in:title"` 명령을 실행하여 기존 이슈를 검색합니다.
- **존재하지 않는 경우**: 새 이슈를 정상적으로 생성합니다.
- **존재하며 열려있는(OPEN) 경우**: 중복 이슈를 생성하지 않고, 필요한 경우 기존 이슈에 정보를 업데이트하거나 댓글을 추가합니다.
- **존재하지만 닫혀있는(CLOSED) 경우**: `gh issue reopen <이슈번호>` 명령어로 해당 이슈를 다시 열고, 재오픈 사유를 설명하는 댓글을 추가합니다.

> [!IMPORTANT]
> **즉시 출력 규칙**: 이슈를 생성하거나 재오픈한 직후, 반드시 아래 형식으로 이슈번호와 제목을 즉시 출력합니다:
> ```
> #<이슈번호> <이슈 제목>
> ```
> 예: `#301 feat: 로그인 API 구현`

### 2. 이슈 속성 지정 (라벨 및 담당자 사후 안내)
- **라벨(Labels)**: `--label "<라벨명>"` 옵션을 사용하여 이슈의 성격(예: `bug`, `enhancement`, `documentation` 등)에 맞는 라벨을 반드시 부여합니다.
- **담당자(Assignees)**: 특별히 지정된 담당자가 따로 없다면 기본적으로 `--assignee "@me"`를 사용하여 주 개발자 계정을 담당자로 지정합니다.
- **[중요] 담당자 사후 인지 고지**: 이슈 생성 완료 후 결과 보고 시, 담당자가 `@me`로 기본 지정되었음을 명시하고 변경 가능 여부를 안내합니다 (§13.6 출력 템플릿 참조).

#### ⛔ 허용 라벨 제한 — 아래 목록 외 라벨 사용 금지:

| 라벨 | 사용 시점 |
|---|---|
| `bug` | 동작 오류 |
| `documentation` | 문서 추가·개선 |
| `duplicate` | 중복 이슈/PR |
| `enhancement` | 신규 기능·개선 요청 |
| `good first issue` | 입문자 적합 |
| `help wanted` | 추가 관심 필요 |
| `invalid` | 유효하지 않은 이슈 |
| `question` | 추가 정보 요청 |
| `wontfix` | 수정 계획 없음 |
| `refactor` | 기능 변경 없는 코드 리팩토링 |
| `in progress` | 작업 진행 중 |
| `pending` | 결정·의존성·조치 대기 (`on hold`, `처리 중` 대체) |
| `severity: critical` | 긴급 — 즉시 조치 필요 |
| `severity: blocker` | 차단 — 출시 불가 |
| `severity: major` | 주요 — 핵심 기능 영향 |
| `severity: minor` | 경미 — 제한적 영향 |
| `severity: trivial` | 사소 — 외형적·저영향 |
| `verified` | QA 또는 사람이 테스트 완료 |
| `human` | 사람의 검토·수동 조치 필요 (자동화 불가) |

> **절대 규칙**: `in-progress`(하이픈), `on hold`, `처리 중` 등 목록에 없는 라벨을 사용하지 않는다.
> 적합한 라벨이 없으면 가장 가까운 항목을 사용하거나 사용자에게 확인한다.

### 3. 거대 이슈 세분화 및 하위 이슈 계층 구조 관리
요청된 작업이나 이슈의 범위가 너무 넓거나 광대하다면, 이를 단일 이슈로 크게 가져가지 말고 반드시 **세부적인 하위 이슈(Sub-issues)들로 잘게 쪼개어 생성**해야 합니다. 각각의 이슈는 하나의 명확하고 구체적인 작업 단위로서 가능한 한 **신속하게 완료 및 종료(Close) 처리**할 수 있도록 Agile한 크기로 설계합니다.
1. **상위 이슈(Parent Issue)**를 먼저 생성합니다.
2. 각 세부 작업을 위한 **하위 이슈(Sub-issues)**들을 쪼개어 순차적으로 생성합니다.
3. **상호 링크 설정**:
   - 하위 이슈 본문에는 상위 이슈 번호를 명시합니다 (예: `상위 이슈: #<상위이슈번호>`).
   - 상위 이슈 본문에는 하위 이슈들을 체크리스트 형태로 기재하고, 작업이 진행됨에 따라 원 이슈(상위 이슈)에 계속해서 연결 및 업데이트하여 진척도를 관리합니다 (예: `- [ ] #<하위이슈번호>`).

### 4. 표준 템플릿 구조 (한글 단독 / 한영 병기 선택)

프로젝트의 `language-policy` 스킬 또는 사용자의 명시적 요청에 따라 한영 병기 형식을 선택할 수 있습니다. **별도 언급이 없으면 한글 전용(Korean-Only)이 기본값**입니다.

#### A. 이슈 표준 템플릿
- **제목 (한글 단독 - 소문자 접두어)**: `카테고리: 한글 제목` (대괄호 없이 소문자 접두어를 사용하며, 항상 소문자만 사용합니다. 예: `feat: 회원가입 기능 추가`, `fix: 로그인 에러 수정`)
- **제목 (한영 병기 - 대괄호 형태)**: `카테고리: English Title / 한글 제목` (예: `fix: Login Error / 로그인 에러 수정`)
- **본문**: 모든 섹션은 다음 표준 레이아웃을 엄격히 준수합니다. 한영 병기 시 각 섹션에 영어와 한글을 순차 배치하며, 한글 전용(Korean-Only) 정책 시에는 번역 없이 순수 한글로만 작성합니다.

```markdown
### 배경 및 목표 (Background & Objective)
[이 작업을 수행하게 된 배경과 최종 달성하고자 하는 목표를 설명합니다.]
[English description if bilingual...]

### 주요 작업 내용 (Key Tasks)
1. **[작업 1 제목 (Task 1)]**
   - [작업 1에 대한 상세 세부 행동 지침 및 설명]
2. **[작업 2 제목 (Task 2)]**
   - [작업 2에 대한 상세 세부 행동 지침 및 설명]

### 작업 환경 (Environment)
- [OS, 셸, 라이브러리 버전 등 개발/구동 환경 정보를 기술합니다.]
```

#### B. Pull Request (PR) 표준 템플릿
- **제목 (한글 단독)**: `카테고리: #이슈번호 한글 제목` (예: `feat: #12 로그인 API 구현`)
- **제목 (한영 병기)**: `카테고리: #이슈번호 English Title / 한글 제목` (예: `feat: #12 Implement Login API / 로그인 API 구현`)
- **본문**: 관련 이슈 자동 닫기 처리와 작업 내용을 명확히 기록합니다.

```markdown
### 배경 및 목적 (Background & Purpose)
- 관련 이슈: Closes #<이슈번호> (Closes를 명시하여 머지 시 연동된 이슈가 자동 종료되도록 유도)
- [이 PR을 작성하게 된 배경과 해결하려는 목적을 기술합니다.]

### 주요 변경 사항 (Key Changes)
1. **[변경사항 1 제목]**
   - [핵심 코드 수정 내역 및 변경된 로직을 상세히 설명합니다.]
2. **[변경사항 2 제목]**
   - [핵심 코드 수정 내역 및 변경된 로직을 상세히 설명합니다.]

### 검증 결과 (E2E / 수동 테스트)
- [테스트 명령어 실행 결과, 콘솔 로그, 혹은 기능 확인 경로를 기술합니다.]
- (UI 변경인 경우) 반드시 수동 테스트 결과 스크린샷 또는 GIF 녹화 파일 첨부
```

### 5. `gh` CLI 빠른 레퍼런스

| 작업 | 명령어 | 비고 |
| :--- | :--- | :--- |
| **이슈 검색** | `gh issue list --state all --search "..."` | 중복 확인용 |
| **이슈 생성** | `gh issue create --title "..." --body-file tmp/issue_body.md --assignee "@me" --label "..."` | `--body-file` 권장 |
| **이슈 기본 조회** | `gh issue view <번호>` | 본문 + 최신 코멘트만 표시 |
| **이슈 전체 조회** | `gh issue view <번호> --comments` | 전체 댓글 히스토리 확인 필수 |
| **이슈 JSON 조회** | `gh issue view <번호> --json assignees,labels,state` | 사전 충돌 점검용 |
| **이슈 리오픈** | `gh issue reopen <번호>` | 재오픈 사유 댓글 필수 |
| **이슈 편집** | `gh issue edit <번호> --title "..." --body "..."` | |
| **이슈 라벨 변경** | `gh issue edit <번호> --add-label "..." --remove-label "..."` | |
| **이슈 종료** | `gh issue close <번호>` | 반드시 사용자 확인 후 |
| **이슈 댓글 추가** | `gh issue comment <번호> --body-file tmp/comment_body.md` | |

> [!TIP]
> **기본 조회** vs **전체 조회**: `gh issue view`는 본문과 최근 댓글만 보여줍니다. 이슈의 전체 맥락과 피드백 이력을 파악하려면 반드시 `--comments` 플래그를 추가하세요.

### 6. 줄바꿈 버그 및 터미널 파싱 에러 방지 (github-cli 통합)
AI 에이전트가 `gh` 명령어를 사용하여 이슈, PR, 코멘트를 생성할 때 줄바꿈 문자(`\n`)가 리터럴 글자로 노출되는 현상을 완벽히 방지해야 합니다.
- **안전한 파일 전달 기법 사용 (적극 권장)**: 다중 마크다운 서식이 들어가거나 내용이 길 때는 반드시 임시 마크다운 파일을 생성한 후 `--body-file` (또는 `-F`) 옵션을 사용하십시오.
- **[경고] 프로젝트 외부 경로 사용 금지**: `/tmp`와 같이 프로젝트 외부 경로를 절대로 사용하지 마십시오. 반드시 **프로젝트 내부의 `tmp/` 디렉터리**(예: `tmp/issue_body.md` 또는 `tmp/pr_body.md`)에 생성한 뒤, CLI 실행이 완료되면 즉시 안전하게 파일 제거(`rm`)를 수행하십시오.

*올바른 실행 명령어 예시:*
```bash
# 1. 워크스페이스 내부 임시 파일 작성
mkdir -p tmp && cat << 'EOF' > tmp/issue_body.md
### 배경 및 목표
설정 페이지 UI 개선 프로젝트입니다.

### 주요 작업 내용
1. **레이아웃 수정**
   - 2단 그리드로 변경
EOF

# 2. --body-file 옵션을 사용하여 생성
gh issue create --title "feat: 설정 페이지 UI 리팩토링" --body-file tmp/issue_body.md --assignee "@me" --label "enhancement"

# 3. 임시 파일 삭제로 워크스페이스 정리
rm tmp/issue_body.md
```

### 7. 글로벌 Anti-Strikethrough 규칙 준수
- **취소선 버그 예방**: 마크다운 본문 내에서 범위나 대략적인 수치(예: 10-20일, 80-90% 등)를 표현하는 과정에서 물결표(`~`)를 사용하면 렌더링 환경에 따라 텍스트 전체에 취소선(Strikethrough)이 그어지는 치명적인 버그가 발생합니다.
- **대체 문자 강제**: 본문 작성 시 물결표(`~`)를 범위 표시에 절대 사용하지 마십시오. 대신 **대시(`-`) 또는 `에서` 등의 표현을 활용**하십시오.
- **예외적 사용 시 이스케이프**: 불가피하게 물결표 기호를 단독으로 노출해야 한다면 백슬래시(`\~`)를 붙여 이스케이프 처리하거나 양옆에 공백(` ~ `)을 두어 렌더러가 잘못 해석하지 않도록 조치하십시오.

### 8. 이슈 작업 시 브랜치 관리 규칙
- **기본 원칙**: 별도 언급이 없으면 **별도 브랜치를 생성하지 않고 현재 브랜치에서 작업**합니다.
- **생성 조건**: 대규모 작업으로 예상될 때만 사용자에게 "**대규모 작업으로 예상되는데 별도 브랜치를 생성할까요?**"라고 먼저 확인한 후 동의를 얻어 생성합니다.
- **종료 조건**: (별도 브랜치를 생성하여 작업했을 경우) 작업을 마친 후에는 반드시 "**직전 브랜치에 머지하고 브랜치 삭제할까요?**"라고 사용자에게 확인합니다.
- **브랜치명 관례**: 생성 시 `feat/#<이슈번호>-<설명>` 또는 `fix/#<이슈번호>-<설명>` 형식을 사용합니다.

### 9. `commit-all` 스킬과의 시너지
- **커밋-이슈 추적성 확보**: 이슈 해결 과정에서 발생하는 모든 개별 작업 단위 커밋은 `commit-all` 스킬을 준수하되, 커밋 메시지 제목에 **이슈 번호 (예: `feat: #123 로그인 API 구현`)를 명확히 기재**하여 커밋 이력과 이슈 간의 완벽한 상호 링크 및 추적성을 보장합니다.

### 10. 이슈 라이프사이클 및 상태 관리 (종료/리오픈/펜딩 상태 관리)
이슈의 상태 전이(종료, 리오픈, 펜딩/보류) 시 다음 규칙을 엄격히 준수하여 사용자 의사를 묻고 알맞은 라벨을 할당합니다.

1. **이슈 완전 종료 (Complete & Close):**
   - **규칙**: 이슈의 모든 작업이 완료되고 검증되었더라도 독단적으로 이슈를 닫지 마십시오. 항상 사용자에게 먼저 동의를 구합니다.
     - *질문 예시: "이슈를 완전히 종료할까요?"*
   - **조치**: 사용자의 승인을 받으면 `gh issue close <이슈번호>`를 실행하고 `completed` 또는 `resolved` 라벨을 부착/확인합니다.

2. **리오픈 및 펜딩/보류 (Reopen & Pending/In-Hold):**
   - **리오픈 (Reopen)**: 추가 버그 발생이나 정책 변경으로 이슈를 다시 열어야 할 때, 사용자에게 추가 요구사항이나 사유를 명확히 질문합니다.
     - *질문 예시: "어떤 추가 수정 사항이나 버그로 인해 이슈를 리오픈해야 할까요?"*
     - 질문 후 `gh issue reopen <이슈번호>`를 실행하고 `reopened` 혹은 `in-progress` 라벨을 적용합니다.
   - **펜딩/보류 (Pending/In-Hold)**: 정책 결정 대기, 외부 의존성 문제, 혹은 관계자 논의가 필요하여 작업을 일시 중단해야 할 때, 사용자에게 보류 필요성을 묻습니다.
     - *질문 예시: "어떤 정책 결정이나 외부 의존성으로 인해 이 작업을 보류(Pending/In-Hold) 상태로 둘까요?"*
     - 질문 후 상황에 맞게 `pending` 혹은 `hold` 라벨을 부착합니다.

### 11. 이슈 작업 개시 및 자동 할당 트리거 — 사전 충돌 점검 포함
사용자가 특정 이슈에 대해 작업을 개시하겠다는 명시적인 의사 표시(예: "이 이슈 처리하자", "이슈 해결하자", "작업 시작하자" 등)를 수행하는 즉시, **아래 순서대로** 동작해야 합니다:

1. **대상 이슈 번호 추출**: 요청 맥락이나 활성 대화 내용으로부터 대상 이슈 번호를 추출합니다.
2. **사전 충돌 점검 (필수 — 어떤 수정 명령도 실행하기 전에 먼저 수행)**:
   이슈의 현재 상태를 조회하여 담당자와 라벨을 정밀하게 확인합니다:
   ```bash
   gh issue view <이슈번호> --json assignees,labels,state
   ```
   조회 결과에 따라 다음 시나리오를 판별합니다:
   - **다른 사람이 이미 할당된 경우**: `assignees` 목록에 `@me`가 아닌 다른 사용자가 존재할 경우, 사용자에게 **반드시** 다음과 같이 경고 메시지를 출력하고 응답을 기다려야 합니다:
     > ⚠️ **경고**: 이슈 #`<이슈번호>`에 이미 **`<사용자명>`** 님이 담당자로 지정되어 있습니다.
     > 그래도 담당자를 본인으로 변경하고 작업을 시작하시겠습니까? **예 / 아니오**로 답해 주세요.
     *이미 `@me`에게 할당되어 있다면 경고를 건너뜁니다 (본인이므로).*
   - **이미 진행 중(in-progress) 상태인 경우**: `labels` 목록에 `in-progress`가 존재할 경우, 사용자에게 **반드시** 다음과 같이 경고 메시지를 출력하고 응답을 기다려야 합니다:
     > ⚠️ **경고**: 이슈 #`<이슈번호>`는 이미 **진행 중(in-progress)** 상태입니다.
     > 그래도 본인이 작업을 이어받으시겠습니까? **예 / 아니오**로 답해 주세요.
   - **두 조건 모두 해당하는 경우**: 두 경고를 함께 보여주고 사용자의 최종 확인을 기다립니다.
   - **응답 대기 (STOP)**: 사용자가 "예", "응", "그래", "진행해" 등 긍정적인 답변을 명시적으로 보낼 때까지 다음 단계로 절대로 진행하지 마십시오. 사용자가 거부하면 작업을 즉각 중단합니다.
3. **이슈 자동 할당** (사용자 확인 후 또는 충돌이 없는 경우에만):
   ```bash
   gh issue edit <이슈번호> --add-assignee "@me"
   ```
4. **진행 중 상태 변경** (사용자 확인 후 또는 충돌이 없는 경우에만):
   이슈의 라벨에 `in-progress`를 추가하고, 기존의 대기 상태를 나타내는 불필요한 라벨(`reopened`, `pending`, `hold` 등)이 있다면 이를 완벽히 정리합니다:
   ```bash
   gh issue edit <이슈번호> --add-label "in-progress" --remove-label "reopened,pending,hold"
   ```
5. **결과 보고, 초간단 요약 및 기획 연동 안내**: 변경이 성공적으로 완료되었음을 사용자에게 명확히 보고합니다. **이때 해당 이슈의 내용을 최대한 축약하고 쉽게 설명해야 합니다 (장황한 원문 그대로 출력 금지).** 요약 후 "더 자세한 설명이 필요하신가요?"라고 사용자에게 물어보세요. 그 후 프로젝트 규칙이나 워크플로우에 따라 기획에 착수합니다.

### 12. 단순 이슈 등록 시 추가 작업 금지 (Standalone Issue Creation only)
사용자가 "이슈 등록해줘", "이슈 생성해줘" 등 단순히 이슈를 시스템에 등록해달라고 요청할 경우:
1. **단독 생성만 수행**: `gh issue create` 명령어를 안전하게 완성하고 실행 제안하여 오직 이슈만 등록합니다.
2. **개발 연동 부가 작업 배제**: 이슈가 생성되었다고 해도 로컬 Git 브랜치를 생성/전환하거나, 다른 기획/작업 문서를 자동으로 수정하지 않습니다.
3. **즉각적 작업 종결**: 이슈 생성이 끝나는 즉시 사용자에게 생성 완료 보고(웹 링크 포함)를 정중히 올리고, 다른 어떠한 개발 진척 행위도 개시하지 않은 채로 그 자리에서 작업을 깨끗하게 끝마칩니다.

### 14. GitHub CLI(`gh`) 샌드박스 바이패스 및 명령어 분리 수칙
1. **샌드박스 바이패스 권한 지정 (`BypassSandbox: true`)**:
   - `gh issue` 등 GitHub API 아웃바운드 통신이 필수적인 명령어를 호출할 때는 샌드박스 네트워크 차단 에러(`HTTP 403 Forbidden`)가 노출되지 않도록 1차 실행 시부터 네트워크 권한(`BypassSandbox: true`)을 지정하여 호출합니다.
2. **단일 커맨드 실행 (커맨드 체이닝 금지)**:
   - `git status && gh issue list`와 같이 네트워크가 필요 없는 로컬 git 명령어와 `gh` API 명령어를 `&&`로 결합하여 사용하지 않고 별도 터미널 실행으로 명확히 분리 수행합니다.

### 13. 워크플로우 단계 (Workflow Steps)
1. **컨텍스트 분석 및 댓글 확인 여부 판단 (Understand Context & Determine Comment Check)**:
   - 사용자의 요청, 작업 범위, 환경을 종합 분석합니다. 대규모 또는 모호한 태스크일 경우 **작은 이슈 단위로 쪼갤 준비**를 마칩니다.
   - 필요 시 과거 이슈 댓글 분석 여부를 확인하기 위해 `gh issue view <이슈번호> --comments`를 실행합니다.
2. **중복 확인 및 계층화 검토 (Check Existence & Determine Hierarchy)**:
   - 기존 이슈를 검색하여 중복 생성을 원천 방어합니다.
   - 작업의 크기가 방대하다고 판단되면 **상위 이슈 및 하위 이슈 체크리스트 계획**을 세웁니다.
   - **[이슈 작업 시작 상황]**: 사용자가 "이슈 처리하자" 등의 작업 개시를 요청하는 경우, **11번 항목**의 사전 충돌 점검을 먼저 수행하여 이미 다른 사람에게 할당되었거나 in-progress 상태인지 확인한 뒤, 해당 시 경고 메시지를 출력하고 사용자의 명시적인 확인을 받은 후에만 자동 할당 및 상태 변경을 실행합니다.
   - **[단순 이슈 등록 상황]**: 사용자가 "이슈 등록해줘" 등의 단순 생성을 요청하는 경우, **12번 항목**의 단독 생성 가이드를 준수하여 브랜치/기획 연동 행위를 완전히 배제합니다.
3. **한글 콘텐츠 초안 및 템플릿 작성 (Draft Content)**:
   - 본 가이드라인의 표준 이슈/PR 한글 템플릿을 기반으로 명확한 초안을 작성합니다.
   - 이때 마크다운 범위 표시에 물결표(`~`)가 사용되지 않았는지 검수하고, 대시(`-`) 등으로 변경합니다.
4. **안전한 명령어 실행 (Execute Command)**:
   - 워크스페이스 내부의 `tmp/issue_body.md` 등의 임시 마크다운 파일을 생성한 후 `gh` 명령어를 실행하고 즉시 파일을 삭제합니다.
   - 담당자는 `--assignee "@me"`로 기본 지정하되, 별도 라벨을 부여합니다.
5. **개발 브랜치 생성 및 머지 처리 (Develop & Merge)**:
   - 별도 언급이 없으면 현재 브랜치에서 작업을 진행합니다. 대규모 작업일 경우에만 사용자에게 별도 브랜치 생성 여부를 묻고 생성합니다.
   - 별도 브랜치 작업이 완료된 후에는 반드시 "직전 브랜치에 머지하고 브랜치를 삭제할까요?"라고 질문하여 동의를 얻습니다.
   - 향후 PR 작성 시 `Closes #<이슈번호>`가 포함되도록 사전 기획을 완료합니다.
6. **결과 보고 및 담당자 변경 권고 (Report Back)**:
   - **[필수 출력 템플릿]**: 이슈가 성공적으로 생성, 재오픈 또는 편집되었을 때, 아래 형식을 사용하여 사용자에게 즉시 눈에 띄게 보고합니다:
     ```
     #<이슈번호> <이슈 제목>
     이슈 링크: <이슈 URL>
     담당자: @me (변경이 필요하시면 말씀해 주세요)
     ```
     예: `#301 feat: 로그인 API 구현`
   - 만약 단순 이슈 등록 건이었다면, 추가 브랜치 생성이나 문서 연동을 배제한 채 여기서 작업을 완전히 종료합니다.

### 14. UI 이슈 증거 캡처 (Before / After)

UI 변경 이슈의 경우 변경 전후 증거를 체계적으로 수집한다:

- **Before**: 코드 변경 전 스테이징 환경에서 캡처한다.
- **After**: 로컬 개발 서버(`http://localhost:3000`)에서 스테이징 API를 바라보며 캡처한다.

헬퍼 스크립트가 있는 프로젝트에서는 아래 방식을 활용할 수 있다:
```bash
# 이슈 N에 대한 before/after 디렉터리 생성 및 환경 확인
<package-manager> issue:evidence:init <N>

# 환경 및 개발 서버 스모크 체크
<package-manager> issue:evidence:check
```

증거 파일은 `tmp/issues/<N>/` 하위에 둔다. 저장소 루트에 `issues/<N>/`을 직접 생성하지 않는다.

| :--- | :--- |
